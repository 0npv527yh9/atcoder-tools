# TODO 駆動リファクタリング

リポジトリルートの `TODO.md` にある番号付き項目を扱うときに使う。

## 作業フロー

1. 計画や編集の前に、指定された番号の項目を `TODO.md` で確認する。番号指定がない場合は「番号指定がない場合の選定」に従い、次に取り組む候補を自動で判断する。
2. `rg`、関連ファイルの読解、必要に応じたテストやビルドで現在の実装を調査する。
3. その項目が現在のコードベースで何を意味するかを、関連ファイル、挙動、リスクとあわせて整理する。
4. 問題点と解決策を整理し、「実装前の設計レビュー」に従って別エージェントにレビューさせる。
5. 設計中に決定判断が必要な場合は、必ずユーザーに意見を求める。意味のある方針が複数ある場合も、プラン確定前にユーザーへ確認する。
6. 主担当が設計とレビュー結果を統合し、責務境界・TODO 間の切り分け・過剰設計の有無を整理する。
7. Plan Mode では、意思決定済みの `<proposed_plan>` を作成し、ファイル編集はしない。
8. Default Mode では、ユーザーがプランを了承した後、または明示的に実装を依頼した後にだけ実装する。
9. 実装後はテストを通し、「実装後レビュー」に従って別エージェントにレビューさせる。重大な指摘があれば修正し、任意の改善指摘は作業完了後にユーザーへ提示する。

## 番号指定がない場合の選定

- `TODO.md` の未完了項目を優先度順に確認し、単純に一番若い番号へ飛びつかず、直近の変更・現在の設計の流れ・次の作業のブロッカー解消効果を加味して候補を選ぶ。
- 原則として P0 を最優先する。ただし、直近作業の流れから P1/P2 の項目を先に片付ける方が後続作業の判断を大きく簡単にする場合は、その理由を明示して候補にできる。
- 候補は通常 1 つを推奨し、必要なら代替候補を 2 つまで添える。各候補について「なぜ今やる価値があるか」「重さやリスク」「次の TODO へのつながり」を短く説明する。
- ユーザーが「次はどれ」「おすすめは」など相談しているだけなら、勝手に実装へ進まず候補提示に留める。ユーザーが番号や候補を選んだら、その項目の調査・整理へ進む。
- ユーザーが「指定がなければ進めて」など自動選定と実行を明示した場合は、推奨候補を選び、その番号の通常フローとして扱う。

## 実装前の設計レビュー

- Plan Mode か Default Mode かに関係なく、実装前に必ず設計を行い、別エージェントにレビューさせる。
- 設計レビュー用エージェントには、現状コードを読んだうえで、主担当の設計案について責務混在、TODO の範囲外への踏み込み、将来作業との衝突、過剰設計・中途半端な抽象化を重点的に見てもらう。
- 主担当はレビュー結果を鵜呑みにせず、自分で統合し、必要なら設計を修正する。
- 設計中に決定判断が必要な場合は、必ずユーザーに意見を求める。ユーザー確認が必要な状態のまま実装へ進まない。
- エージェントには必ず「ファイル編集しない」と明示する。Plan Mode では特に、主担当もエージェントもファイル編集しない。
- エージェントを起動した場合は、結果を回収した後に必ず close する。

## 実装後レビュー

- 実装完了後、必要なフォーマット・テスト・確認コマンドを通してから、実装前レビューとは別のエージェントにレビューさせる。
- 実装後レビュー用エージェントには、実際の差分、テスト結果、TODO の範囲、既存挙動の維持、重大な回帰の有無を重点的に見てもらう。
- 重大な指摘が見つかった場合は、主担当が内容を確認して修正し、必要な確認コマンドを再実行する。
- 任意の改善指摘や後続 TODO に回すべき指摘がある場合は、作業完了後にユーザーへ提示する。必要なら `TODO.md` への追加を提案する。
- エージェントを起動した場合は、結果を回収した後に必ず close する。

## 実装ルール

- 実装作業の前に新しいブランチを切る。ユーザーが別名を指定しない限り、`todo/<number>-<short-slug>` を使う。
- 作業が自然に複数段階へ分かれる場合は、段階的に実装する。無関係なリファクタリングを同じ段階へ混ぜない。
- 段階的なチェックリストが役立つ場合は、`ignore/` 配下に Markdown チェックリストを作成する。
- ユーザーの変更を保持する。無関係な変更を戻したり上書きしたりしない。
- `AGENTS.md` にあるこのリポジトリの Rust とアーキテクチャ方針を守る。ページ種別付き型を維持し、副作用は薄い境界へ閉じ込め、app/use-case ロジックをテストしやすくする。
- サンプルコードを示す場合は Rust を使う。

## 新しい発見

- 調査中に別の実在する問題が見つかった場合は、適切な優先度と粒度でルートの `TODO.md` に追加する。
- 今回の作業では修正しないが、後続で対応すべき設計負債や暫定配置を見つけた場合も、重複を確認したうえで `TODO.md` に追加する。すぐ追加しない判断をした場合は、ユーザーに TODO 追加を提案する。
- 追加前に既存の `TODO.md` 項目を確認し、重複を避ける。
- 追加する TODO は実行可能な内容にする。古い scratch メモや曖昧な迷いをそのまま戻さない。

## Skill の更新

- 会話や作業の中で、このワークフローを改善する再利用可能なルールが見つかった場合は、この skill を更新する。
- Plan Mode では、skill 更新内容を proposed plan に含める。
- Default Mode では、作業の一部として関連する skill ファイルを更新し、可能なら検証する。

## Commit 対応

- ユーザーが `commit` と言ったら、現在の差分を確認し、関連する変更だけを commit する。
- 実際の変更内容を反映した commit message を書く。
- 無関係な dirty work を commit に含めない。
